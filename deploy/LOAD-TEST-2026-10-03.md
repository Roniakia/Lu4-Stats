## Method and limitations

Five alternating routes: players, clans, batched player histories, feed with24-hour interval, options. Server rotated over gamma/white/black/carmine. Each stage dispatched requests for up to15seconds or300 requests, then waited for in-flight work; request timeout12seconds. Results are completed requests per total elapsed time, not an offered rate or open-arrival capacity.

Repeat stages used fixed seven-day date ranges and batches of nine real Gamma player names, allowing coalescing and15-second cache reuse. Distinct stages varied end timestamps and requested1–90day ranges with up to72 real Gamma names. Those names can be absent on other servers, making some responses smaller; this is not a worst-case populated72-member party on every server. Distinct feed/options paths still repeat, and underlying caches remain available. There was no deliberate cache flush.

Feed was the slowest route: baseline slowest3.33s; at eight distinct workers feed p95/slowest8.33s. The histories route p95 reached4.39s in that stage. Whole-workload percentile improvements between the first and later repeat stages reflect warmer caches and different request totals; they do not imply concurrency makes uncached work faster.

Short samples miss possible memory/CPU peaks and long-term growth. No browser rendering, image proxy/CDN, TLS/reverse proxy overhead, pagination beyond the first feed page, empty-search worst case, overnight soak, home-upload failure, or maximum populated four-month/year query was tested. Homelab CPU/RAM/disk I/O/SQL plans were not measured, so the results cannot isolate SQL versus transfer versus app computation. HTTP200 alone does not prove semantic correctness for every returned row; existing contract/smoke checks are separate.

## Practical interpretation

The current cheap server remained stable for this dataset and short tests. Cached/shared reads reached about19–22requests/s; distinct heavier reads reached about5–6requests/s with seconds of tail latency. This is not a sustained production capacity guarantee, nor proof of1,000 daily users under synchronized expensive requests. Daily users must be translated into requests per visit and peak arrival rates before sizing.

CPU pressure and feed latency deserve attention before widening concurrency. Profile feed SQL, transferred snapshot size, and JavaScript event construction separately; consider materializing events at ingestion and caching first-page feed results by latest collection/interval with correct cursor/date limits. Review expensive-query admission and overload status handling. Keep maximum party/date bounds. Re-test against realistically populated multi-month synthetic data on isolated staging, then perform a longer soak and measure homelab resources. Preserve memory headroom for the future HTTPS proxy and tunnel. No tuning or hardware changes were made as part of this test.

At24 concurrency all captured503 responses explicitly said 'The app is busy. Please retry shortly.' with Retry-After5. The admission guard limits distinct active/queued reads (two active, sixteen queued, five-second queue timeout); cache/coalescing and differing work duration mean HTTP concurrency is not identical to distinct queued database work. The first16 run did not capture response bodies, so its503 cause is not individually proven. A warmer16 repeat passed, demonstrating variable rather than a sharp deterministic boundary.

Sampled memory peaked at169.1MiB in the additional tests. No OOM kills or automatic restarts were observed. CPU reached roughly its0.8-core quota in the first16 test. The final burst was stopped after overload appeared; no higher stage was attempted. Database-only performance cannot be inferred from these end-to-end runs. A practical initial target is fewer than eight simultaneous expensive requests, not eight online users: a single browser can issue multiple requests. Twelve-to-sixteen heavy requests can wait several seconds, and24 can produce substantial bounded rejection. This is not an advertised capacity guarantee.

Next: optimize/profile feed, make client overload handling respect Retry-After without synchronized retry storms, verify realistic long-history data and sustained arrivals on staging. Raising queue length or concurrency alone may worsen latency/resource pressure. The deployed configuration was not changed.
